# InkWeaver Agent 功能临时开发计划

> 状态：临时方案（v0.2）
>
> 目标：以现有 RAG、搜索、文档和同步能力为基础，建设能够规划任务、调用文档工具、综合多篇资料、生成并保存新文档的 Knowledge Work Agent，并作为 InkWeaver 最终 AI 能力体系的核心。
>
> v1 边界：不实现联网搜索、多 Agent、定时自主运行、插件市场或 Agent+Node 图形化编排；这些能力进入后续阶段，不影响 v1 先完成本地知识工作闭环。
>
> 定位：本文既描述 Agent v1 的可交付范围，也定义其进入最终 AI 功能体系前必须满足的安全、可靠性、质量和扩展边界。

## 0. 当前模块地图与收尾顺序（2026-09-21 更新）

本节是当前实现进度与近期执行顺序的入口；后文产品能力、数据库目标字段和阶段描述不代表均已实现。统一产品入口为“对话 / 任务”，两者共用 Agent 基础；旧 Quick Ask 接口仅作为兼容迁移对象，不作为永久独立体系。

### 当前执行约定（覆盖后文历史交付节奏）

- 按最新授权连续完成 v1 剩余开发，最终统一交付审阅，不再每单元停下确认。

- `activeProfile` 选择模型配置；每个 profile 管理 `adapter/baseUrl/model/apiKeyEnv/toolCalling/temperature/timeoutMs`。文件只放密钥环境变量名，不放密钥。首版适配 OpenAI-compatible 协议；其他协议仍需新增适配器实现。
- `limits` 管理上下文、单次输出、每 Run/每用户 UTC 日调用次数与累计预占 Token 额度。累计额度在用户锁内写入调用记录，并发、失败、重试、重启均计入；按完整 `contextTokens` 保守预占且不返还，不能将其理解为实际账单或金额上限。实际 usage 独立保存，未知仍为 null。
- 正式业务库迁移、部署和发布仍未授权；专用隔离数据库沿用既有授权。

### 本轮交付：模型 Tool Calling 往返（2026-09-20）

本单元是 Graph 编排的前置能力，不代表 Graph、Checkpoint 或完整 Agent 已完成。

- `agent-model-tools.ts`：按用户即时策略、Run 固定版本筛选 builtin/L0 工具，支持待确认工具的发现；发现不代表资源授权或确认通过。
- `AgentModelClient.step()`：每次只做一次模型决策，返回 `answer` 或 `tool_calls`；只向模型发送名称、描述和输入 Schema。权限、来源和版本留在服务端。
- 工具调用与结果消息必须按 ID 配对。未知工具、重复 ID、孤立/重复/缺失结果、损坏参数 JSON 不会被静默降级为普通回答；具体参数 Schema 仍由 `ToolCallPreparer` 校验。
- `complete()` 保留纯文本接口并强制禁用工具；适配器声明 Tool Calling 协议支持，不保证已配置供应商支持该能力，不支持时调用失败而非悄悄降级。
- 单步最多暴露 32 个工具、接收 8 个调用提议，参数最多 64 KiB、深度最多 32。供应商并行调用请求关闭；返回多个提议不代表执行器并发执行。
- 下一编排单元需把工具定义、调用参数和结果消息计入完整上下文预算；本单元协议大小上限不替代模型 Token 预算。模型调用 ID 不是业务 `callKey`，服务端恢复去重仍依赖业务记录。
- 改动文件：`agent-model-tools.ts`、`agent-model.client.ts`、`agent-model.client.test.ts` 和本文。没有新增依赖、数据库表、运行入口或真实工具调用。
- 验证：服务端构建、全仓类型检查、3 个变更 TypeScript 文件 lint 和 4 项定向测试通过。全仓 lint 仍被未修改的 editor-core/editor-mobile/admin/sync-client 等既有错误阻塞。供应商调用、数据库与端到端验收按约定留待整版。

### 本轮交付：LangGraph / PostgreSQL Checkpoint 内部执行链（2026-09-20）

- 固定依赖 `@langchain/langgraph@1.4.16`、`@langchain/langgraph-checkpoint-postgres@1.0.5`；采用官方 StateGraph/PostgresSaver，没有自建另一套 Checkpoint 格式。
- `agent-graph.ts`：初始化上下文 → 模型决策 → 顺序工具调用 → 再次模型决策 → 最终业务提交。默认最多 10 次模型决策；工具 Schema/参数/结果计入估算输入预算，配对消息不能截断，超预算保留检查点并报错。
- `agent-graph.runner.ts`：仅供服务端调用，接受归属正确、存在 Thread、`workflowVersion=agent-read-v1` 的 Run。构建前从数据库加载用户/Run；每个节点复核状态，权限从可信回调重新获取，不保存在 Checkpoint 中。
- 独立 PostgreSQL 会话 advisory lock 串行化同一 Run；不跨模型调用持有业务事务。使用 `durability=sync`，模型提议检查点提交后才进入工具节点。框架键固定为 userId:runId，不接受调用方指定任意 checkpoint_id。
- 工具逻辑键固定为 graph-v1:轮次:位置，先保存业务 Call，再授权/执行。恢复时复用已提交结果，不重复调用；EXECUTING/RETRY_WAIT/OUTCOME_UNKNOWN 暂停并等待既有恢复模块处理，不直接重放。
- 确认暂停使用 LangGraph interrupt；resume 只唤醒图，仍重新查询确认状态。拒绝/过期使等待中的 Run 失败；批准后回到 QUEUED/RUNNING 并再次授权执行。
- 回答写入与 Run COMPLETED 在同一业务事务提交。业务已完成而框架提交失败时，再调用入口直接返回完成，避免重复回复。模型/数据库错误不被自动掩盖为成功或无限重试。
- `1790121600000-CreateAgentCheckpoints.ts` 固定官方 1.0.5 的 0~4 版表结构：独立 agent_checkpoint schema，checkpoints/checkpoint_blobs/checkpoint_writes 均通过 agent_runs.checkpointKey 外键级联。迁移未执行。运行时工厂只检查迁移版本，不自动 setup/执行 DDL；连接池由未来 AgentModule 管理，须指向同一业务库。
- 用户导出包含按 Run 归属读取的 Checkpoint/Blob/Write，二进制使用 base64；删除 Run 时框架数据同事务级联，迟到写入不能重建已删除 Run 的 Checkpoint。
- 已完成真实 StateGraph + MemorySaver 的正常循环、结果提交后节点失败恢复、重复 resume 仍待审批、预算/键隔离的离线检查。这里的工具业务端口为测试替身，不冒充真实 PostgreSQL 并发或进程崩溃验收。
- 验证：服务端构建、全仓 `pnpm typecheck`、7 个变更 TypeScript 文件 lint、17 项定向测试通过；全仓 lint 被既有 sync-client/editor-core/editor-mobile 等错误阻塞。没有执行迁移、Docker 或真实模型调用。
- 尚未开放 AgentModule/队列/API/UI。最终引用合法性、cited 标记及模型 usage 持久化尚未接通，不能把当前回答称为“引用已验证”。整版验收还需覆盖 advisory 锁断连、真实结果/Checkpoint 提交竞争及取消时在途请求。
- 设计参考：[官方 PostgresSaver](https://reference.langchain.com/javascript/langchain-langgraph-checkpoint-postgres/index/PostgresSaver)；实际 DDL 与本地固定版本包的 migrations 实现核对。

#### 0.4.2 全流程与事务划分

```text
统一会话输入 → 固定 Run 目标、来源范围、工作流版本
  → 编排提出工具调用
  → Catalog / Policy / Schema 重新检查 → 保存固定调用参数与来源身份
  → 解析具体资源需求 → 查询当前资源权限及版本
  → 需要确认：保存绑定记录 → 用户确认 → 等待执行前再次复核
  → 领取事务：检查 Run/Call、确认、预算和租约 → 预留预算 + START + Attempt + Event
  → 提交事务 → 调用适配器（数据库事务之外）
  → 结果校验/大小限制 → 完成事务：校验执行代次 + 保存结果 + 结算预算 + 状态/事件
  → 编排推进 → 带引用回答或草稿 → 确认保存 → 完成 Run
```

- 执行模块拥有领取/完成事务，Graph 只提出下一步，不直接修改 Call/Attempt。具体方法名可在实施时确定，事务所有权不再分散。
- 等待用户、模型请求和外部工具调用均不持有数据库事务。资源授权预检查存在时间窗口，实际读写仍须由文档服务再次限定归属，写操作同时校验目标版本。
- 确认通过不直接 START。领取事务检查确认仍有效、调用参数与目标版本未变，消费或绑定确认；重试复用同一逻辑操作的确认需仍在有效期内且内容未变，权限和预算每次复核。
- attemptId 匹配不代替租约；回写必须同时满足当前执行代次。过期 Worker 不得提交，外部副作用未知时不自动当作失败重试。
- 本地文档写入的幂等记录与文档创建在同一事务；幂等键按逻辑调用/成果版本固定，不能每轮 attempt 重新生成。
- Checkpoint 不作为业务状态权威。不得假定框架保存与业务写入天然同事务：先持久化业务结果，恢复时按 callKey 识别已处理调用再推进 Graph，避免恢复重复写入。

| 2 | 受控工具执行与恢复 | 使用第 1 项结果领取调用、预留预算、执行一个真实只读文档工具、校验/保存结果；拒绝旧代次、处理超时取消及有限重试 | 集中完成执行上下文、租约、预算、结果持久化与受控入口；先确定全模块后编码，不拆成逐字段补丁 |
| 3 | 统一会话与只读 Agent | 保存消息，模型通过同一执行模块调用检索/读取工具，回答带来源，可按已提交业务结果恢复 | 复用 RAG；在此选定并验证 Graph/Checkpoint 适配方式，再创建其表；不先单独做框架原型 |
| 4 | 成果生成与幂等保存 | 多文档综合为有版本的草稿，经确认保存文档；重复投递不重复保存 | 先有成果版本与操作幂等表，再注册写工具，复用第 1、2 项 |
| 5 | 统一对话/任务工作台 | 认证 API、历史/SSE、来源展示、确认交互、草稿编辑与完整用户路径 | 使用前面固定的业务服务；此时再补用户暂缓的接口端到端验收，不提前逐层做 UI |
| 6 | v1 发布收尾 | 针对真实完整链路检查质量、成本、恢复和兼容迁移，明确开放范围 | 复用已有测试，仅补实际缺口；不趁收尾扩大功能 |

**第 1、2 项执行模块已完成内部实现，见 0.3.4～0.3.6；第 3 项的会话/消息持久化前置代码见 0.3.7，当前只差专用 PostgreSQL 验收。** 验收通过后进入模型/RAG/来源与上下文，不跳到 UI 或 Graph 原型。

## 1. 建设目标

Agent v1 需要完成以下核心闭环：

```text
用户输入任务目标
  → Agent 生成执行计划
  → 确定文档来源范围
  → 搜索并读取相关文档
  → 提取事实、观点、结论和冲突
  → 生成可编辑提纲
  → 综合生成带来源的新草稿
  → 校验引用和内容完整性
  → 用户确认
  → 保存为新的 InkWeaver 文档
```

典型任务示例：

- 综合多篇 Local-First 笔记，生成一篇技术总结。
- 根据指定文件夹中的文档整理项目周报或月报。
- 对比多篇技术方案，生成优缺点与决策建议。
- 汇总多次会议记录，提取决策、风险和待办事项。
- 根据现有资料生成教程、报告、文章草稿或知识手册。
- 在上一次 Agent 草稿基础上扩写、改写或重新组织部分章节。

### 1.1 最终 AI 产品能力图

InkWeaver 的最终 AI 功能不是单一页面或单一接口，而由以下能力层组成：

| 阶段 | 产品能力 | 主要用途 | 本文范围 |
|---|---|---|---|
| AI Phase 1 | Quick Ask | 基于个人知识库快速问答并返回引用 | 已有能力，保留并统一入口 |
| AI Phase 2 | Knowledge Work Agent | 自主规划、研究多篇文档、综合生成新文档 | v1 主体 |
| AI Phase 3 | Editor Copilot | 对选区或章节执行总结、扩写、润色、翻译和基于来源的插入 | v1 设计接口，后续实现 |
| AI Phase 4 | 外部来源与可配置工具 | 在用户授权下连接网页、文件或受控外部服务 | 后续规划 |
| AI Phase 5 | Agent+Node | 图形化编排工具、条件、审批和多步骤工作流 | 后续规划 |

Agent v1 完成后可以称为“Knowledge Work Agent 已完成”，但只有 Quick Ask、Knowledge Work Agent 与 Editor Copilot 形成统一体验后，才可称为 InkWeaver 的完整 AI 功能。

## 2. Agent 功能范围

### 2.1 任务理解与计划

Agent 将自然语言目标转换为结构化执行计划。计划至少包含：

- 任务类型与预期产物。
- 文档来源范围。
- 搜索和读取步骤。
- 资料提取和综合策略。
- 提纲、写作、校验和保存步骤。
- 是否需要用户确认的检查点。

前端应展示计划，并允许用户在正式执行前修改来源范围、输出要求或取消任务。

### 2.2 文档来源范围

支持以下来源选择方式：

1. 用户手动选择若干文档。
2. 选择一个文件夹，并可选择是否包含子文件夹。
3. 输入主题，由 Agent 搜索整个个人知识库。
4. 在 Agent 推荐的候选来源中手动补充或排除文档。

来源范围可以包含：

- `docIds`
- `folderId`
- 是否包含子文件夹
- 标签
- 创建或更新时间范围
- 最大来源数量
- 最低相关性阈值

只有 Agent 实际读取过的文档才能进入最终来源列表和引用列表。

### 2.3 搜索与读取

Agent 复用现有文档和混合搜索能力，实现：

- 关键词、语义和 Smart 混合搜索。
- 按文件夹、标签和时间筛选。
- 获取文档标题、正文和必要元数据。
- 批量读取多篇文档。
- 长文档分段读取，控制模型上下文大小。
- 去除重复或高度相似的来源。
- 对每次读取执行用户归属和权限校验。

Agent 不得通过工具调用绕过现有文档权限。

### 2.4 多文档综合生成

多文档综合是 Agent v1 的核心能力，不能退化为逐篇摘要拼接。

处理流程：

1. **资料提取**：从每篇文档中提取事实、观点、结论、决策、待办和风险。
2. **跨文档综合**：合并重复内容，识别互补信息、时间变化和相互矛盾的结论。
3. **结构设计**：依据用户目标生成文章结构和章节提纲。
4. **草稿生成**：根据综合结果生成完整、连贯的新文档。
5. **结果校验**：检查关键结论是否有来源、引用是否有效、是否遗漏重要材料。

首版支持的输出类型：

- 综合总结
- 技术方案
- 项目报告
- 周报或月报
- 对比分析
- 会议纪要汇总
- 教程
- 文章草稿
- 决策记录
- 待办清单
- 自定义结构文档

生成参数包括标题、文档类型、目标读者、语气、长度、输出语言、目标文件夹、标签，以及是否包含摘要和引用。

### 2.5 提纲与草稿

默认工作流：

```text
提取资料
  → 生成提纲
  → 可选用户确认
  → 生成草稿
  → 自动检查
  → 用户预览
  → 保存新文档
```

用户可以：

- 修改提纲后继续。
- 扩写、缩写或重写指定章节。
- 删除章节或调整章节顺序。
- 改变文风、长度或目标读者。
- 补充新的来源文档后继续生成。
- 重新生成部分内容，而不是每次重跑全部任务。
- 保存、放弃或继续修改当前草稿。

### 2.6 引用与来源追踪

Agent 生成的文档应具备可追溯来源：

- 保存实际读取的来源文档 ID、标题和使用片段。
- 正文支持 `[#1]` 形式的引用标记。
- 文末可生成“参考文档”章节。
- 点击引用可以打开对应的原始文档。
- 删除未使用、越界或无法解析的引用。
- 保存生成时使用的来源摘要和文档更新时间，避免原文变化后无法解释历史结果。

来源关系由 Agent 数据表保存，不能只依赖正文中的标题文本。

### 2.7 新建与修改文档

Agent 可以：

- 将生成结果保存为普通 InkWeaver 文档。
- 指定标题、标签和目标文件夹。
- 将输出文档与 `agentRunId`、来源文档建立关联。
- 继续修改本次 Agent 创建的草稿。
- 让 Agent 生成的文档继续参与搜索、同步和后续 Agent 任务。

安全规则：

- 默认生成新文档，不修改来源文档。
- 修改本次 Agent 创建的草稿允许直接执行。
- 修改用户已有文档前必须获得明确确认。
- 在完整版本历史功能实现前，不允许 Agent 静默覆盖已有文档。
- 保存操作必须幂等，任务重试不能生成重复文档。

### 2.8 运行控制

每个 Agent Run 支持：

- 查看执行计划、当前步骤和整体进度。
- 查看正在调用的工具及其状态。
- 查看已搜索、已读取和已引用的来源。
- 流式接收执行事件。
- 在关键写操作前等待用户确认。
- 主动取消、失败重试和从 Checkpoint 恢复。
- Server 重启后恢复未完成任务。
- 查询历史任务及其最终产物。

运行限制至少包括：

- 最大执行步骤数。
- 最大工具调用次数。
- 最大来源文档数。
- 最大读取字符数或 Token 数。
- 单工具超时和整个任务超时。
- 最大重试次数和用户并发任务数。

### 2.9 连续对话与任务上下文

Agent 不能只支持一次性 Run，还需要支持围绕同一目标持续修订：

- 一个 `AgentThread` 包含多条用户消息、Agent 回复和一个或多个 Run。
- 用户可以针对上次结果继续提出“扩写第三章”“排除某篇来源”“改成面向非技术人员”等要求。
- 新 Run 可以继承上一次的来源范围、提纲、输出参数和 Artifact，也允许用户显式清空上下文。
- 每次修订保留父 Run 和 Artifact 版本关系，支持回看而不是覆盖历史结果。
- 对话历史只提供任务上下文，不自动扩大文档访问权限或写工具权限。
- 进入模型上下文的历史消息需要裁剪或摘要，并保留用户最新明确要求。

### 2.10 Agent 生成内容与递归来源

文档来源需要标识内容出处：

- `human-authored`：主要由用户编写。
- `agent-generated`：由 Agent 生成并保存。
- `mixed`：用户与 Agent 共同修改。

默认优先使用人工文档。用户可以选择是否允许 Agent 生成文档继续作为来源。若使用 Agent 生成内容作为来源，必须沿来源链保留原始人工文档，避免 AI 内容被反复摘要和循环放大。

### 2.11 Editor Copilot 接口预留

Agent v1 不实现完整 Editor Copilot，但数据和 API 设计需要预留以下能力：

- 对选中文本或指定章节执行总结、扩写、改写、润色和翻译。
- 根据已选来源生成一个新章节并插入草稿。
- 以 Diff 形式展示修改，允许逐项接受或拒绝。
- 不覆盖用户尚未同步的本地 Yjs 编辑。
- Copilot 操作也记录来源、模型用量和确认结果。

Editor Copilot 后续应复用 Agent 的模型客户端、来源追踪、权限策略、Artifact 和评测体系，不能重新建立一套独立 AI 基础设施。

## 3. 首版工具清单

| 工具 | 作用 | 写操作 |
|---|---|---:|
| `search_documents` | 使用现有混合搜索查找候选文档 | 否 |
| `list_folder_documents` | 枚举指定文件夹及其子目录中的文档 | 否 |
| `get_document_metadata` | 获取标题、标签、目录和时间等元数据 | 否 |
| `read_document` | 读取单篇文档的完整内容 | 否 |
| `read_documents_batch` | 批量读取已选择的来源文档 | 否 |
| `create_document` | 将最终草稿保存为新的 InkWeaver 文档 | 是 |
| `update_agent_draft` | 更新本次 Agent 创建的草稿 | 是 |

工具通过 `ToolDefinition` 声明输入与输出 JSON Schema，当前使用 Ajv 8.18.0 按 JSON Schema 2020-12 严格模式校验，不绑定 Zod。模型不能直接拼接 SQL、访问数据库或自行调用内部地址。

提纲生成、资料提取、综合写作和引用校验属于 Agent Graph 内部节点，不包装成外部工具。

工具按风险分级：

| 等级 | 类型 | 默认策略 |
|---|---|---|
| L0 | 搜索、枚举和读取 | 自动执行，但每次仍校验用户权限 |
| L1 | 创建新的 Agent 草稿或新文档 | 根据 Run 创建时的确认策略执行 |
| L2 | 修改用户已有文档 | 必须逐次明确确认；v1 默认关闭 |
| L3 | 删除、公开分享或外部写入 | v1 不向 Agent 开放 |

工具执行权限由 Server 策略决定，模型输出只能提出调用请求，不能自行授权。确认令牌需要绑定 `runId`、工具名称、规范化参数摘要和过期时间，防止确认后参数被替换。

### 3.1 工具装配与调用流程

> 更新日期：2026-09-10。以下为已确认的目标流程，适用于统一 Agent 体系的“对话 / 任务”两种模式。当前实现范围见 3.2，不能将流程图视为已完成的执行链。

**工具装配阶段**：在启用工具时编译 Schema，调用时复用，不为每次调用重复编译。

```text
可信工具定义 ToolDefinition
  → ToolRegistry 校验描述结构并注册
  → 取得定义快照
  → ToolSchemaValidator 编译输入、输出 Schema
  → 编译成功后，绑定同一版本的定义、校验器与执行适配器
  → 纳入可调用工具集合（仍须逐次授权）
```

- 注册成功不等于可调用；编译失败必须阻止工具进入可调用集合，不能降级为跳过校验。
- 工具定义变化后重新装配，不能仅按名称继续使用旧校验器；运行固定版本必须与装配版本一致。
- 不可信工具/插件经隔离执行与序列化边界接入，宿主使用不带自定义 reviver 的 `JSON.parse` 解码，再进入校验器。解析后不混入插件对象，也不在宿主内对不可信可执行对象调用 `JSON.stringify` 来替代隔离。
- 工具 Schema 由可信接入层审查后装配；外部工具发现结果不直接成为已批准的定义。

**每次调用阶段**：策略预检查先于参数校验，具体资源授权与参数绑定确认在参数校验之后。

```text
调用请求：工具名称、参数
  → 检查认证主体与当前 Run 状态
  → ToolPolicy 预检查：允许列表、注册状态、固定版本、风险、业务权限、MCP 连接权限
  → 未被拒绝后执行 validateInput
  → 检查具体资源归属与访问权限
  → 需要确认时，绑定本次参数与版本发起确认
  → 执行前复核授权、取消状态、确认有效性，并检查/预留预算
  → 执行适配器调用工具：超时、取消、幂等与重试控制
  → 限制结果大小，经序列化数据边界解码结果
  → validateOutput
  → 结果处理：资源引用检查、内容块校验、上下文预算处理
  → 进入模型上下文 / 保存允许持久化的结果
```

- `confirmation_required` 表示仍待确认，不是执行许可。确认绑定 Run、工具版本、具体参数及有效期；等待期间权限或任务状态变化，执行前必须重新判断。
- `allowed` 仅表示策略预检查通过，不替代参数、资源、预算和执行前复核。
- 资源的 MIME、大小、处理状态和权限以服务端权威记录为准，不能只信任输入声明。
- Schema 校验不自动转换类型、补默认值或删除字段；额外字段是否允许由 Schema 控制。当前未启用格式扩展、异步校验或远程 Schema 加载，未支持的定义编译失败。
- 输出 Schema 通过只证明格式符合契约，不证明内容真实可信；工具结果仍按不可信数据处理，不直接无上限进入模型或数据库。
- 输出校验失败不能撤销已经发生的写操作。执行层必须记录实际执行状态，失败输出不能作为成功结果使用，也不能因此盲目重试写工具。
- 错误/审计状态可以单独记录，但不得借此持久化未经允许的完整原始结果或敏感错误内容。

### 3.2 当前实现范围

截至 2026-09-10，工具装配目录已串联结构校验、Schema 编译与适配器绑定；调用准备链已串联策略预检查、装配解析与输入校验，尚未接入 Nest/API 或真正执行工具：

| 组件 | 已实现 | 尚不负责 |
|---|---|---|
| `ToolDefinition` / `ToolRegistry` | 工具描述、结构检查、注册、查询副本、撤销、重复名称保护 | Schema 编译、执行适配器绑定、用户授权 |
| `ToolSchemaValidator` | 构造时编译输入/输出 Schema，调用时校验，稳定错误码 | 资源真实性与权限、执行 |
| `ToolCatalog` | 结构校验与编译成功后发布；绑定同名、同版本、同来源适配器；按版本解析、撤销；向策略层提供已装配定义 | 真正执行、用户授权、Nest/API 接入 |
| `ToolPolicy` | 基于可信上下文检查身份、允许列表、版本、风险、业务权限及 MCP 连接权限 | 认证系统接入、确认令牌验证、预算、具体资源授权 |
| `ToolCallPreparer` | 策略拒绝优先；按版本解析装配句柄；校验独立参数快照；返回是否需要后续确认 | Run 状态、资源授权、发起/验证确认、预算、执行 |
| `AgentContentBlock` / `parseAgentContentBlock` | 内容块契约及 JSON 数据格式校验，默认只开放文本 | 媒体能力开放、资源读取与鉴权 |

`ToolPolicy` 当前默认只开放 L0；显式开放 L1-L3 后也至少返回待确认，可使用 `ToolCatalog` 查询已装配定义。Run 状态检查、确认、预算、资源授权、真实执行、重试控制与结果处理均为后续工作。

`ToolCatalog.resolve` 返回服务端装配句柄，不执行工具或授予权限。撤销会阻止后续发现与解析，但无法收回调用方已取得的函数引用；未来执行层必须在执行前重新解析并复核授权，不得长期缓存句柄。

`ToolCallPreparer.prepare` 的 `prepared` 只表示策略预检查和参数校验通过，返回用户 ID、工具名称/版本、参数副本及 `requiresConfirmation` 标记，不返回执行函数。该结果不是授权凭证或确认令牌；修改参数、等待确认或进入真实执行时，仍须完成后续检查与必要的重新校验。

代码入口：`apps/server/src/modules/agent/tools/`、`packages/shared/src/types/agent-content.ts`、`packages/shared/src/utils/agentContent.ts`。

### 3.3 调用记录、确认与恢复生命周期（调用/尝试持久化已实现，执行控制待实现）

> 更新日期：2026-09-14。`tool-call-lifecycle.ts` 已实现纯状态转换及测试，不代表已具备调用持久化、确认或执行能力。工具调用状态与第 4 节的 Run 状态分别管理，一个 Run 可以包含多次工具调用。

**准备层的定位**：保留 `ToolCallPreparer` 作为纯准备组件，供首次请求和恢复后的重新校验复用；不让它承担数据库、确认交互或执行职责。当前 `PreparedToolCall` 是临时参数副本，后续调用记录接收它，但不能直接把它当成完整持久化实体或授权凭证。

#### 3.3.1 一次逻辑调用与多次执行尝试

- 一次逻辑调用使用服务端 `callId`，关联 `runId`、当前用户及确定的工具名称、版本、来源身份。重新投递同一次调用沿用 `callId`，不能在每次队列消费时重新生成。
- 调用记录保存经校验的参数快照，以及适用的目标资源/成果版本条件。用户修改参数或目标后生成新调用，旧调用在执行前取消，旧确认不再适用。
- 每次实际尝试拥有独立 `attemptId`、尝试序号、执行代次和起止时间。重试沿用逻辑调用及幂等关联，但不覆盖之前的尝试结果。
- 参数可能包含私人内容，只保存在受用户归属与生命周期约束的存储中；日志和可见事件只保存必要摘要。记录中不包含适配器函数、凭据或签名下载 URL。

#### 3.3.2 主流程与状态含义

```text
请求通过 prepare
  → PREPARED：调用记录已保存，尚未完成资源授权
  → 检查具体资源权限与版本条件
  → 需要确认：WAITING_CONFIRMATION → 用户确认 → READY
    无需确认：READY
  → 执行前复核并领取执行权
  → EXECUTING
  → 成功结果通过输出与结果处理：SUCCEEDED
```

| 状态 | 含义与退出条件 |
|---|---|
| `PREPARED` | 参数和工具选择已固定；资源检查通过后进入待确认或待调度，失败进入 `FAILED` |
| `WAITING_CONFIRMATION` | 等待用户批准本次具体操作；拒绝进入 `CANCELLED`，确认到期进入 `EXPIRED` |
| `READY` | 等待执行调度，不是长期有效的授权；执行前仍需重新检查 |
| `EXECUTING` | 当前尝试已领取执行权，可能产生副作用；失败不能自动解释为“未执行” |
| `RETRY_WAIT` | 已确定符合安全重试条件，等待退避；到期重新走执行前检查，不能直接调用适配器 |
| `OUTCOME_UNKNOWN` | 中断或超时后无法判断写操作是否发生，禁止盲目重试；先查询幂等结果或对账 |
| `SUCCEEDED` | 结果满足输出契约且允许保存的结果已记录，终态 |
| `FAILED` | 已确定失败，或重试耗尽；保留副作用是否已提交的独立记录，终态 |
| `CANCELLED` | 执行前取消，或执行中确认已停止且没有写副作用；终态 |
| `EXPIRED` | 执行前确认/调用有效期届满，未启动新尝试；终态 |

终态不重新执行。用户重新发起任务时创建新逻辑调用，并按具体操作处理已存在的成果。

当前领域模型使用 `createToolCallLifecycle` 创建初始值，`transitionToolCall` 返回新的状态，非法迁移抛出稳定错误，不修改输入对象。初始值的创建不表示调用已落库。`attemptCount` 仅在 `START` 时增加，持久化层现已同步创建独立尝试记录及 attemptId（见 0.3.2），Worker 租约仍待执行单元。

模型事件是可信上层核验后提交的事实，不是用户可直接调用的命令：`CONFIRMED` 不自行验证确认令牌，`START` 不自行取得执行权，`RETRY_SCHEDULED` 不自行证明幂等保证或预算充足。副作用信息描述整个逻辑调用，而不是只描述最后一次尝试。

执行中取消只记录 `cancelRequested`；确认整体无副作用且执行停止后才可取消。幂等恢复等待中的未知副作用会继续保留，取消或到期转入 `OUTCOME_UNKNOWN` 等待对账，不伪装成未执行的终态。终态拒绝重复完成事件，事件去重由后续持久化层处理。

#### 3.3.3 确认绑定及执行前复核

- 确认由服务端生成，关联用户、Run、callId、工具版本与来源、参数摘要、目标资源版本条件和有效期。摘要用于绑定数据，不自行构成授权；具体摘要编码与令牌/记录实现将在确认单元中确定并测试。
- UI 展示即将执行的实际操作、目标和关键参数。确认记录由已认证用户提交，不能接受模型提供的 `confirmed: true`。
- 接收确认只使调用进入 `READY`；服务重启后保留确认记录，但不恢复旧权限判定。
- 领取执行权前重新检查：Run 未取消、工具仍装配且版本/来源一致、当前权限及资源归属有效、参数仍符合 Schema、目标版本条件成立、所需确认有效、预算可预留。
- 工具不再可用、来源连接变化、资源版本条件失效或授权撤销时，不静默替换工具或继续写入；记录明确失败原因。需要更改参数/目标的操作重新准备并确认。
- 数据库使用条件更新/执行代次控制同一调用的领取，调用状态、尝试记录和本地预算预留应协调提交。用户取消与领取执行权必须有明确的串行判定，不能只依赖先查后写。
- 通用复核不能消除所有资源竞争。具体写工具仍须在写事务中检查归属、版本条件和幂等约束；外部服务只能按其提供的原子性保证执行。

#### 3.3.4 取消、重试与不确定结果

- 执行前取消直接阻止后续领取；执行中先记录取消请求并传递取消信号，不能仅因用户点击取消就宣称副作用已撤销。
- 已完成的写入不自动删除。若写入已提交但输出校验失败，记录 `FAILED` 与“副作用已提交”，阻止无幂等保障的重试。
- `retryPolicy=never` 不自动重试；`safe` 仅用于明确可安全重放的适配器，并等待旧尝试结束或被隔离；`idempotency-key` 必须重用同一逻辑操作键，不能每次尝试生成新键。
- 崩溃、超时或断连导致写结果不明时进入 `OUTCOME_UNKNOWN`。只有取得权威结果，或适配器具备经验证的幂等重放保证，才允许结束调用或安排恢复尝试。
- 旧 Worker 失去执行权后不得提交状态或启动新步骤；执行代次不能撤销已经发出的外部请求，外部写入仍需要服务端幂等支持。
- `OUTCOME_UNKNOWN` 对账后：已提交且可恢复合规结果则成功；已提交但结果不可用则失败并标注副作用；确认未提交才根据重试/取消策略继续。仍无法确定时保留该状态并报告需要处理，不伪装为失败且无副作用。

## 4. Agent 状态机

建议使用 `LangGraph.js StateGraph`，建立显式状态流转：

```text
CREATED
  → PLANNING
  → SEARCHING
  → READING
  → EXTRACTING
  → OUTLINING
  → WRITING
  → VERIFYING
  → WAITING_CONFIRMATION
  → SAVING
  → COMPLETED
```

异常终态：

```text
CANCELLED
TIMED_OUT
FAILED
```

Agent State 至少包含：

```typescript
interface AgentState {
  runId: string;
  userId: string;
  goal: string;
  sourceScope: AgentSourceScope;
  plan: AgentPlanStep[];
  currentStep: number;
  sourceCandidates: AgentSource[];
  selectedSources: AgentSource[];
  extractedFacts: ExtractedFact[];
  outline?: AgentOutline;
  draft?: AgentDraft;
  outputDocumentId?: string;
  status: AgentRunStatus;
  toolCallCount: number;
  retryCount: number;
  error?: AgentRunError;
}
```

运行状态通过 PostgreSQL Checkpoint 持久化，长任务由 BullMQ Worker 执行，避免占用 HTTP 请求生命周期。

### 4.1 BullMQ 与 Checkpoint 一致性

- PostgreSQL 中的 Run、Call、Attempt、Result、Message 等业务记录是权威事实；Checkpoint 仅保存编排恢复位置。
- BullMQ 只负责调度和重试，队列状态不能直接替代 Agent Run 状态。
- Worker 领取 Run 时写入带过期时间的租约，并在执行期间发送心跳。
- 同一个 Run 同一时间只能有一个有效 Worker；租约过期后才允许安全接管。
- 业务状态与可见事件同事务；Checkpoint 使用独立事务。先提交业务结果，恢复后按固定 callKey 复用业务事实，再推进 Checkpoint，不假定框架和业务天然同事务。
- 每个节点和写工具执行前后均检查取消状态；服务端确认取消后不得再进入新的写步骤。
- `COMPLETED`、`CANCELLED`、`FAILED`、`TIMED_OUT` 为终态，重复队列消息不得重新执行保存。
- `create_document` 使用 `runId + artifactVersion` 作为幂等范围，由数据库唯一约束阻止重复写入。
- Worker 崩溃恢复、重复投递、确认超时和保存后响应丢失必须有专门测试。

### 6.6 `agent_tool_calls`

当前代码已包含迁移 `CreateAgentToolCalls1789430401000`、实体 `AgentToolCall` 与事务入口 `ToolCallStore`，而非仅有表结构。未启用实体自动同步；迁移负责组合归属外键、Run 内 callKey 唯一约束和字段约束。

- `create`：接收可信准备结果和匹配来源；锁用户后检查 Run。仅 RUNNING 可新建；同键同身份、参数与确认要求返回已有记录，保持原状态；不同内容拒绝。
- `get`：按用户、Run、调用 ID 共同查询。
- `transition`：读取数据库生命周期及修订号，复用纯状态规则，以归属、旧状态与 revision 条件更新；不覆盖参数和工具身份。START 要求 Run 为 RUNNING，终态 Run 不推进调用。
- 新建追加 `TOOL_CALL_CREATED`；更新追加 `TOOL_CALL_STATE_CHANGED`，记录 callId、调用 revision、前后生命周期与原因。仅取消意图变化也有事件。与 Run Writer 共用 `appendAgentEvent`，调用、事件和序号全部提交或回滚；重复建单不追加事件。
- Reader 与 Exporter 通过统一协议解析两类调用事件。协议只表达固定字段，不包含参数、结果或凭据，不证明授权和执行事实。

实体映射既有 17 个字段；JSON 参数使用 `Record<string, unknown>` 规避 TypeORM 递归 Partial 展开，输入必须经过可信准备层校验。方法不直接接受 HTTP/模型事件，不提供执行权限、确认令牌验证、预算或真实适配器调用；独立 attemptId 已实现，见下节。参数快照仍由接入层保证不夹带凭据。

`tool-call.persistence.integration.test.ts` 已覆盖多连接同键去重、修订竞争、事件失败回滚、确认/重试/取消/成功路径、终态保护、共享序号以及导出和清理回滚/级联。2026-09-15 Docker 修复后已实际通过全部断言，本单元数据库验收完成，详见 0.3。

#### 6.6.1 `agent_tool_attempts`

通过 `CreateAgentToolAttempts1789516800000` 创建，复用调用的用户/Run 组合归属；`(callId, attemptNumber)` 唯一，同一调用至多一条 STARTED。保存独立 id、attemptNumber、startRevision、status、startedAt、endedAt，不复制参数、凭据或原始输出。状态为 STARTED / SUCCEEDED / FAILED / OUTCOME_UNKNOWN / CANCELLED。

调用状态及事件仍由 `ToolCallStore.transition` 统一提交；尝试更新在同一事务内执行，错误向外传播。事件正文中的 callId 与 attemptCount 可关联到对应代次，attemptId 从指定代次查询获得。不能把此事务一致性解释成外部操作恰好执行一次。

### 6.7 `agent_run_sources`

保存 `runId`、`docId`、来源标题、使用片段、文档更新时间以及是否进入最终引用。

### 6.8 `agent_artifacts`

保存提纲、草稿、最终内容、Artifact 版本和输出文档关联。

数据库和日志不得保存模型隐藏推理过程，只保存计划、工具调用、来源、结果和错误等可审计信息。

### 6.9 数据生命周期

2026-09-15：导出已追加 `agent.toolCalls`，包含固定工具身份、参数快照及生命周期字段，与 Run/事件共用事务快照。查询同时匹配 Run 和调用用户归属，字段显式列出；不读取适配器或连接凭据。调用表尚未迁移时返回空数组，查询失败不返回部分成功结果。该入口尚未做真实数据库端到端验证；后续写入层仍须阻止凭据进入参数快照。调用记录通过 Run 外键参与已有删除链，无需新增直接删除路径。

2026-09-15：清空数据和注销流程已在原事务内调用 `deleteAgentData`，先锁用户行并检查未结束 Run；存在未结束任务时返回冲突，在任何业务数据/外部对象删除前停止。允许清理时按用户删除 Run，事件由外键级联删除。Writer 创建和更新同样先锁用户行，协调所有经该入口的写入；底层 Store/直接 SQL 绕过仍不受此约定保护。清空提交后仍保留账户，随后新建任务允许创建；本单元不撤销在锁上等待的新建请求，未来任务接入需明确请求失效策略。尚无真实执行器，因此不提供自动取消和等待停止；真实并发、级联与端到端清理待数据库验证。

用户密码校验后的 JSON 导出当前包含 `agent: { threads, messages, runs, events, toolCalls, toolAttempts, confirmations, toolResults, budgetReservations }`。Agent 部分使用独立 REPEATABLE READ 事务快照和用户归属过滤，显式选择字段并校验事件正文；Message 不导出内部 `requestDigest`。兼容不同迁移阶段，实际查询失败仍使导出失败。既有 Run/工具数据库验收已完成；2026-09-18 新增会话表的真实 PostgreSQL 验收因 Docker Desktop 未运行暂未完成，用户接口端到端仍按要求暂缓。

- 所有 Agent 表必须包含明确的用户归属或可追溯到用户，并配置必要的外键和级联删除。
- 用户数据导出需要包含 Thread、用户消息、Run 摘要、来源关系和 Agent 生成的 Artifact。
- “删除全部数据”和“注销账户”必须清理 Agent Thread、Run、Checkpoint、Event、Tool Call、Source 和未保存 Artifact。
- Event、Tool Call 和 Checkpoint 设置可配置保留期限；到期清理不得删除仍在运行任务所需的数据。
- 来源文档删除后保留来源标题和生成时摘要，但 UI 标记“原文已删除”，不得暴露已无权访问的完整历史正文。
- 输出文档删除后可以保留 Run 审计摘要，但清除正文 Artifact，除非用户显式选择保留历史草稿。
- Tool Call 参数、错误和日志默认不保存完整文档正文、密钥、Authorization Header 或模型供应商敏感响应。

## 11. 安全与信任边界

来源文档、历史消息和工具返回值全部视为不可信数据。Agent 必须遵守：

- 系统规则、用户当前目标、历史对话、来源文档和工具结果使用明确分隔的消息层级。
- 文档中出现的“忽略规则”“调用某工具”“发送数据”等内容只能作为被分析文本，不能成为执行指令。
- 模型不能自行增加工具、修改工具风险级别、跳过确认或扩大来源范围。
- 所有文档读取和写入均由 Server 使用当前用户身份重新鉴权。
- 工具参数执行前进行 Schema、资源归属、长度、数量和路径校验。
- 写工具只接受服务端签发且未过期的确认令牌。
- 日志、Event 和模型错误不得返回密钥、Authorization Header、内部连接信息或无权文档内容。
- 建立恶意来源文档、提示词注入、跨用户 ID、伪造确认、参数替换和工具越权测试集。

## 12. 上下文与综合策略

每个 Run 需要在执行前计算上下文预算。建议采用以下分层流程：

```text
候选搜索
  → 相关性重排
  → 来源选择
  → 文档分段
  → 每篇文档结构化事实提取
  → 跨文档事实去重与冲突检测
  → 章节级生成
  → 全文一致性检查
  → 引用校验
```

必须配置：

- 最大候选数、最终来源数和单文档读取量。
- 每个模型节点的输入、输出 Token 上限。
- 文档截断、摘要和分层综合策略。
- 来源不足、上下文溢出和模型拒绝时的降级行为。
- 事实去重键、时间优先规则和冲突保留格式。
- 章节重新生成时使用的最小上下文范围。
- Agent 生成来源的最大递归深度及人工来源回溯规则。

来源不足时，Agent 应明确说明缺少哪些信息，不得用无依据内容填满文档。

## 13. 模型、成本与配额

`AgentModelClient` 负责统一模型能力和调用统计：

- 启动或创建 Run 时验证模型是否支持所需能力。
- Structured Output 解析失败时允许有限次数的 Schema 修复。
- 统一超时、限流、供应商错误和可重试错误分类。
- 记录模型、请求次数、输入 Token、输出 Token、耗时和估算成本。
- 模型不可用时保留 Checkpoint，并向用户返回可恢复状态。
- 不允许静默切换到能力或隐私边界不同的模型。

配额至少包括：

- 每用户并发 Run 上限。
- 每 Run 最大模型调用数和 Token 预算。
- 每日或每月使用量上限。
- 搜索、读取和生成接口的独立限流。
- 达到预算时返回已完成步骤和部分 Artifact，不执行未经确认的保存。

具体数值在模型、部署资源和真实任务基准确定后写入配置，不硬编码在业务逻辑中。

## 14. 数据、隐私与可观测性

- Agent 数据遵循用户数据导出、清空和注销流程。
- 明确各表保留期限和定时清理策略。
- 指标只记录运行状态、耗时、Token、工具错误和队列状态，不记录完整私人正文。
- 关键指标包括任务完成率、节点失败率、恢复次数、取消延迟、队列等待时间、模型耗时、Token 用量和写入幂等冲突数。
- 日志使用 `runId`、`threadId`、`stepId` 和 `toolCallId` 关联，但避免记录用户目标全文和文档正文。
- 健康检查区分 API、Worker、Redis、PostgreSQL、Chat 模型和 Embedding 服务状态。
- 管理和排障接口不得允许管理员直接读取用户文档或完整 Prompt。

| 未实际读取文档进入引用 | 0 |
| 跨用户内容泄漏 | 0 |
| Prompt Injection 导致未授权工具调用 | 0 |
| 有来源事实的引用覆盖率 | ≥ 95% |
| 固定评测集任务完成率 | ≥ 90% |
| 100 次保存重试产生重复文档 | 0 |
| 重复队列投递产生重复写入 | 0 |
| 中断恢复后重复生成最终文档 | 0 |
| SSE 重连丢失已提交事件 | 0 |

评测结果必须记录模型、Prompt 版本、工具版本、数据集版本和配置。仅凭页面演示成功不能认定 Agent 质量通过。

## 16. v1 验收标准

关键 E2E 场景：

> 用户选择一个包含多篇 Local-First 笔记的文件夹，要求 Agent 生成一篇技术总结。Agent 搜索并读取相关文档，展示来源和提纲，综合生成带引用草稿，经用户确认后保存到指定文件夹。最终文档可以正常打开，引用可以跳转，原始文档没有被修改。

同时必须满足：

1. Agent 能生成并执行不少于两个步骤的计划。
2. 搜索、读取、综合和保存形成完整工具调用闭环。
3. 无权文档不可被搜索、读取或引用。
4. 未实际读取的文档不能成为最终引用。
5. 取消后不得继续调用工具或保存文档。
6. Server 重启后能够从 Checkpoint 继续。
7. 保存失败后的重试不能生成重复文档。
8. 来源文档默认保持不变。
9. 工具失败时前端能显示具体步骤、工具和原因。
10. Agent 生成的新文档能够正常参与编辑、搜索、同步和后续 Agent 任务。
11. 同一 Thread 可以基于上一个 Run 继续修订，并保留 Artifact 版本关系。
12. 来源文档中的指令不能改变 Agent 权限或触发未授权写工具。
13. SSE 断线重连能够从最后 Event ID 恢复，事件无丢失且客户端可去重。
14. Worker 崩溃、租约接管和队列重复投递不会产生重复保存。
15. Agent 数据能够随用户导出、清空和注销完整处理。
16. 每个 Run 可以查询模型调用次数、Token 用量、耗时和预算状态。
17. 固定评测集达到第 15 节定义的量化门槛。

## 17. v1 暂不实现

- 联网搜索和外部知识源。
- 多 Agent 协作。
- 定时或无人值守任务。
- 第三方插件和开放工具市场。
- Agent+Node 图形化流程编排。
- Agent 自动覆盖已有文档。
- 完整文档版本历史。
- 移动端 Agent 工作台。

## 18. 最终 AI 完成定义

以下条件全部满足后，才能称为 InkWeaver 的完整 AI 功能：

1. Quick Ask、Knowledge Work Agent 和 Editor Copilot 使用统一入口、来源体系和权限规则。
2. Agent 能完成“现有文档研究 → 多文档综合 → 生成新文档 → 持续修订 → 安全保存”的闭环。
3. 用户能够看到计划、工具、来源、引用、写操作确认、用量和失败原因。
4. 安全、恢复、幂等、数据生命周期和量化评测达到生产门槛。
5. Editor Copilot 能以 Diff 方式修改选区或章节，并正确处理 Yjs 本地与远端状态。
6. 外部工具、Agent+Node 和多 Agent 保持可扩展，但不作为前三项交付的阻塞条件。

v1 先完成“现有文档研究 → 多文档综合 → 生成新文档 → 持续修订 → 用户确认 → 保存和追踪来源”的完整闭环，再进入 Editor Copilot 和后续扩展阶段。
