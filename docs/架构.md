# InkWeaver 架构

InkWeaver（SyncBox-AI）是基于 pnpm 与 Turborepo 的 Local-First 跨端笔记应用。客户端以本地存储和 Yjs 为编辑主路径，通过 HTTP 与 Socket.IO 同步到 NestJS 服务端。

## 1. 仓库分层

```text
SyncBox-AI/
├── apps/       # 可运行应用
├── packages/   # 可复用包
├── deploy/     # 生产部署资产
├── docs/       # 当前架构、UI 与运维文档
├── package.json
├── pnpm-workspace.yaml
└── turbo.json
```

### 应用

| 路径 | 职责 | 主要技术 |
|------|------|----------|
| `apps/server` | REST、Socket.IO 同步、认证、文档、搜索、通知、存储和邮件 | NestJS、TypeORM、PostgreSQL、Redis/BullMQ |
| `apps/web` | PC Web 主客户端 | React、Vite、Dexie、Yjs、TipTap |
| `apps/h5` | 移动 Web 客户端 | React、Vite、Yjs |
| `apps/mobile` | 原生移动客户端 | Expo、React Native、SQLite、Yjs |
| `apps/admin` | 管理后台 | React、Vite |

应用之间不得相互引用；共享能力进入 `packages/`。

### 共享包

| 分组 | 包 | 职责 |
|------|----|------|
| 基础 | `shared`、`assets` | 公共类型、工具和静态资源 |
| 平台 | `adapters` | 存储等适配器 |
| 数据与业务 | `api`、`services` | 客户端 API 访问与可复用业务流程 |
| 本地优先 | `db-adapter`、`sync-engine`、`sync-client` | Web/Native 本地持久化、Yjs 缓存和同步调度、socket 房间订阅与 syncEngine 装配 |
| 编辑器 | `editor-core`、`editor-web`、`editor-mobile` | 编辑器协议与平台实现 |
| 界面 | `ui` | 跨端共享组件与交互封装 |

## 2. Workspace 依赖边界

以下关系来自各 workspace 的 `package.json`；新增依赖时必须继续满足这些方向：

```text
shared、assets
├─ 不依赖其他 workspace 包
│
├─ api、db-adapter、editor-core → shared
├─ adapters → api
├─ editor-web、editor-mobile → editor-core
├─ services → api、shared
├─ sync-engine → db-adapter、shared
├─ sync-client → api、db-adapter、services、shared、sync-engine（装配层，不被任何 package 依赖）
└─ ui → services、shared

apps/server → shared
apps/admin  → adapters、api、services、shared、ui
apps/web    → adapters、api、assets、db-adapter、editor-web、services、shared、sync-client、sync-engine、ui
apps/h5     → adapters、api、assets、db-adapter、editor-web、services、shared、sync-client、sync-engine、ui
apps/mobile → api、editor-mobile、services、shared、sync-engine、ui
```

约束：

- `shared` 保持平台无关；不得反向依赖业务包或应用。
- `sync-engine` 只通过 `db-adapter` 接触本地持久化，不直接引入应用实现。
- `sync-client` 是装配层，不被任何 `packages/*` 依赖；通过依赖注入接收 localDB / authService / documentApi / socketUrl / clientId，避免循环依赖与平台耦合。
- Nest 服务端模块只放在 `apps/server`；`packages/api` 和 `packages/services` 面向客户端复用。
- 编辑器公共协议进入 `editor-core`，Web 与 Native 实现不得互相依赖。

## 3. 本地优先与同步链路

```text
编辑器
  ↓ Yjs update
sync-client（apps 装配：注入 localDB / authService / documentApi / socketUrl）
  ├─ subscribeDocRoom：引用计数管理 join-doc/leave-doc，消除切文档竞态
  ├─ sync-engine：Yjs 缓存、冲突检测
  │   ├─ db-adapter：本地快照与待推送操作
  │   ├─ HTTP：pull / push 与冲突恢复
  │   └─ Socket.IO：/sync 命名空间的实时更新
  └─────────↓
apps/server
  ├─ SyncUpdate / DocSnapshot：CRDT 更新与快照
  ├─ DocumentProjectionService：Yjs 内容投影到 documents
  ├─ AI 索引：投影后切块 → 外置 Embedding HTTP → pgvector（document_chunks）
  └─ PostgreSQL：搜索、列表、分享与向量检索
```

- Web 使用 Dexie/IndexedDB；Native 适配器使用 SQLite。
- `packages/sync-engine` 的内存 Y.Doc 缓存上限为 20 篇。
- Web 快照缓存由 `packages/db-adapter/src/web/index.ts` 控制，当前上限为 20 篇或 200 MB。
- HTTP push 使用 `baseUpdateId` 检测冲突；服务端较新时客户端先 pull，再重试待推送更新。
- Socket.IO 命名空间为 `/sync`，握手传输仍经过 `/socket.io` 路径；Web/H5 开发代理必须同时覆盖两者。
- 第一期 RAG：`POST /api/ai/ask`；向量存储为 PostgreSQL + pgvector（后期可换 Qdrant）；嵌入服务见 `services/embed-service`。

## 4. 服务端边界

- 认证：JWT access/refresh token、会话表与 WebSocket 握手校验。
- 文档：文档、文件夹、回收站与分享读取。
- 同步：增量更新、快照、冲突检测和内容投影。
- 辅助模块：搜索、通知、存储用量、邮件队列、健康检查与 AI（RAG 问答 / 文档向量索引）。
- `/healthz` 只表示进程存活；`/readyz` 检查 Redis 与 PostgreSQL。

服务端实体、DTO 和接口实现是数据结构与 API 行为的事实来源；本文不复制完整接口清单。

### 6.1 搜索（Phase 1 + 搜索方案设计原则）

模块边界：[apps/server/src/modules/search/](file:///d:/Codex_Workspaces/software-development/projects/SyncBox-AI/apps/server/src/modules/search)，`SearchModule` imports `AiModule` 复用其 `EmbeddingClient` 与 `VECTOR_STORE` 导出，不重复建 provider。三端搜索调用契约下沉到 [packages/api/src/search/searchApi.ts](file:///d:/Codex_Workspaces/software-development/projects/SyncBox-AI/packages/api/src/search/searchApi.ts)，按项目依赖边界不新增 `packages/services` 纯转发方法。

四路通道 + 三模式：

- 四路通道（[search.service.ts](file:///d:/Codex_Workspaces/software-development/projects/SyncBox-AI/apps/server/src/modules/search/search.service.ts) 的 `searchExact` / `searchFuzzy` / `searchRelated` / `searchSemantic`）：精确匹配（标题/tags 全包含，AND 语义）、全文模糊（tsvector + GIN 倒排）、关联召回（年月/tags 交集/同文件夹/最近打开，OR 加分）、语义向量（pgvector HNSW ANN）。
- 三模式（`mode` 参数过滤通道）：`smart`（默认，四路全开）、`keyword`（留 exact + fuzzy，丢弃 semantic + related）、`semantic`（留 exact + semantic，丢弃 fuzzy + related）。
- 统一入口 `hybridSearch()`：`Promise.all` 四路并行 + 每路 `.catch(() => [])` 降级（须配对 `logger.warn` 让失败可见），`Map<docId>` 文档级合并 + `WEIGHTS` 加权求和 + `recencyBonus` 时效加分 + 归一化排序 + 分页。
- 路由：`GET /api/search/hybrid?q=&mode=smart|keyword|semantic&page=1&pageSize=10`（[search.controller.ts](file:///d:/Codex_Workspaces/software-development/projects/SyncBox-AI/apps/server/src/modules/search/search.controller.ts)）。

关键表与索引：

- `documents.docTsv tsvector` + GIN 倒排索引（标题 `setweight('A')` + 正文 10 万字截断后 `setweight('D')`，由 `createDocument`/`updateDocument` 调用 `updateDocTsv()` 增量维护）。
- `document_chunks.embedding vector(512)` + HNSW 索引（`opclass vector_cosine_ops`，`m=16`、`efConstruction=128`，运行时 `hnsw.ef_search=128` 在事务内 `SET LOCAL` 生效不污染连接池）。

搜索设计原则（来自搜索方案设计，作为 Phase 1 的设计依据补充）：

- 设计目标：可召回（四路覆盖不同匹配意图）、排序准（精确顶置 + 语义合理 + 结构化加权）、不重复（`Map<docId>` 文档级去重保证跨页不重复、`total` 准确）、性能可接受（10 万分块量级 P95 < 500ms）、可演进（权重/阈值/分词策略灰度调整无需改代码结构）。
- HNSW 选型理由：相比精确 KNN（全表扫 O(N)）与 IVFFlat（聚类失效需重训），HNSW 增量插入 recall 不退化、默认参数跨数据量级稳定、运维成本接近 0，是生产环境默认选择。
- 加权求和 vs RRF：四路分数同尺度（0~100 或 CASE 线性叠加），加权求和天然可解释；RRF 基于排名丢弃分数幅度信息（第 1 名与第 500 名差距被压缩），故选加权求和。
- 召回边界靠操作符语义区分：exact 用 `@>`（AND 全包含）、related 用 `?|`（OR 任一重叠）、fuzzy 用 `ts_rank_cd`（覆盖密度排名）、semantic 用余弦距离 `<=>`。jsonb 列的操作符必须与列类型严格对齐，详见 [技术笔记 #8](./notes/笔记-08-PostgreSQL-数组与-jsonb-操作符语义边界.md)。
- 上限策略：fuzzy/related/exact 单通道候选 LIMIT 500，semantic 通道 HNSW topK 固定 5000 + 余弦距离硬阈值 0.7（相似度 < 30% 的噪声挡在池外），合并后 `total >= 3000` 时 `truncated=true` 前端提示细化关键词。
- 演进路线：T4 权重调优（基于用户点击反馈微调 `WEIGHTS`）→ T5 中文分词增强（接入 zhparser 替换 `simple` 字典）→ T6 权重迁配置表动态调。
