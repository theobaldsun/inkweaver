# InkWeaver 部署与发布

本文是 InkWeaver 当前生产发布的完整操作手册。即使没有历史会话，也应能依照本文完成代码更新、低内存部署、验收和故障恢复。

本文假设生产环境为 Ubuntu ECS，代码目录为 `/opt/inkweaver/repo`，Web 静态目录为 `/opt/inkweaver/web`，Compose 项目名为 `repo`。实际主机、域名和 SSH 私钥只保存在本机 `deploy/INSTANCE.local.md`，不要提交到 Git。

## 1. 当前部署拓扑

```text
开发机（Windows + Git Bash）
├─ 构建 Web dist ── scp/ssh ──> /opt/inkweaver/web ──> Nginx
├─ 构建 Nest dist/镜像 ───────> repo-server:latest ──> inkweaver-server
└─ 本机 embedding :8090 ── frpc ──> ECS frps :18090 ──> Nest 容器

ECS Docker Compose
├─ inkweaver-server
├─ inkweaver-postgres
├─ inkweaver-redis
└─ inkweaver-minio

ECS 独立服务
├─ Nginx
├─ FRPS
└─ Shadowsocks（不属于 InkWeaver Compose，发布时不得操作）
```

当前 ECS 内存约 1.6GB。不得在业务容器运行期间直接构建 Web，也不得把 Server `build --no-cache` 当成常规发布方式。

## 2. 三类备份必须区分

| 类型 | 示例 | 策略 |
|------|------|------|
| 发布临时回滚 | `web.previous.<release>`、`repo-server:pre-deploy-*` | 只在发布验收期间保留；成功后清除 |
| Git 源码快照 | `repo.previous.<timestamp>` | 仅在重新 clone/替换源码目录时人工创建和人工清理 |
| 业务数据备份 | `/opt/inkweaver/backups/pg_*.sql.gz`、`uploads_*.tar.gz` | 必须保留并按备份策略轮换，禁止随镜像清理 |

删除发布回滚镜像时，不要运行无边界的 `docker system prune -a`，也不要删除 PostgreSQL、MinIO volume。

## 3. 发布前检查

### 3.1 本机

Windows 使用 Git Bash。`C:\Windows\System32\bash.exe` 是 WSL 入口；没有安装 WSL 时会报 `/bin/bash: No such file or directory`，这不是项目脚本故障。

```bash
cd /d/Codex_Workspaces/software-development/projects/SyncBox-AI

git status --short --branch
git fetch origin
git rev-parse HEAD

node --version
pnpm --version
ssh -V
scp -V 2>&1 | head -n 1
```

要求：

- 工作区修改已经明确归属；不要覆盖未提交的用户改动。
- `pnpm-lock.yaml` 与提交一致。
- SSH 私钥存在且权限可被 Git 自带 OpenSSH 接受。
- 本机 embedding 与 frpc 是否运行不影响 Web 构建，但会影响 AI 生产验收。

### 3.2 ECS

```bash
ssh -i /path/to/key.pem root@your-ecs

free -h
df -h
docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}'
systemctl is-active nginx frps
ss -lntp | grep -E ':3000|:7000|:18090'
curl -fsS http://127.0.0.1:3000/readyz
```

确认 Shadowsocks、PostgreSQL、Redis、MinIO、Server、Nginx 和 FRPS 都处于预期状态。若 SSH、HTTPS 或 Shadowsocks 已经异常，先恢复服务器，不要继续构建或发布。

### 3.3 业务数据备份

```bash
cd /opt/inkweaver/repo
sudo bash deploy/scripts/backup.sh
```

该脚本备份 PostgreSQL 和 uploads。它不是 Nest 镜像备份，不能因“当前版本稳定”而跳过。

## 4. 更新 ECS 源码

### 4.1 正常 Git 仓库

源码通常由 `admin` 所有，root 登录后用正确用户执行 Git：

```bash
sudo -u admin git -C /opt/inkweaver/repo status --short --branch
sudo -u admin git -C /opt/inkweaver/repo fetch origin
sudo -u admin git -C /opt/inkweaver/repo pull --ff-only origin master
sudo -u admin git -C /opt/inkweaver/repo rev-parse HEAD
```

`fatal: detected dubious ownership` 表示当前 Unix 用户与仓库所有者不一致。优先使用仓库所有者执行 Git，或修正明确目录的所有权；不要为了省事把所有目录加入全局 `safe.directory`。

### 4.2 目录不是 Git 仓库

`fatal: not a git repository` 说明当前目录没有 `.git`，不是 `git status` 命令的问题。先保存生产配置，再 clone：

```bash
sudo install -d -m 700 /opt/inkweaver/config
sudo install -m 600 /opt/inkweaver/repo/.env.prod /opt/inkweaver/config/.env.prod

sudo mv /opt/inkweaver/repo "/opt/inkweaver/repo.previous.$(date +%Y%m%d_%H%M%S)"
sudo -u admin git clone https://github.com/theobaldsun/inkweaver.git /opt/inkweaver/repo
sudo install -m 600 /opt/inkweaver/config/.env.prod /opt/inkweaver/repo/.env.prod
```

`repo.previous.<timestamp>` 是旧源码目录快照，不参与运行。确认新仓库、配置和容器都正常后再人工决定是否删除。

## 5. `.env.prod` 的实际位置

Compose 文件同时使用变量插值和 `env_file`：

```bash
cd /opt/inkweaver/repo
docker compose -p repo -f docker-compose.prod.yml --env-file .env.prod config >/dev/null
```

因此执行 Compose 时，生效文件是 `/opt/inkweaver/repo/.env.prod`。`apps/server/.env` 只用于本地开发，而且 `.dockerignore` 排除了 `.env*`，不会自动进入生产镜像。

建议把 `/opt/inkweaver/config/.env.prod` 作为服务器上的受控副本，在重新 clone 后用 `install -m 600` 恢复到仓库根目录。不要提交任何真实 `.env.prod`。

AI 生产配置至少包括：

```env
AI_CHAT_BASE_URL=https://provider.example/v1
AI_CHAT_API_KEY=replace-with-secret
AI_CHAT_MODEL=model-name
AI_EMBED_BASE_URL=http://host.docker.internal:18090
AI_EMBED_TOKEN=replace-with-http-service-token
AI_EMBED_TIMEOUT_MS=60000
```

`AI_EMBED_TOKEN` 是 Nest 调用 embedding HTTP API 的 Bearer Token，不是 frpc 登录 frps 的 Token。

## 6. Docker Compose 命令解析

```bash
docker compose \
  -p repo \
  -f docker-compose.prod.yml \
  --env-file .env.prod \
  up -d --build
```

| 参数 | 含义 |
|------|------|
| `docker compose` | 使用 Docker Compose v2 |
| `-p repo` | Compose 项目名；决定默认镜像、网络、volume 的名称前缀 |
| `-f docker-compose.prod.yml` | 指定生产编排文件 |
| `--env-file .env.prod` | 为 Compose 插值提供生产变量 |
| `up` | 按配置创建或协调服务 |
| `-d` | 后台运行 |
| `--build` | 启动前构建需要构建的镜像；不代表禁用缓存 |

在资源充足的 CI/服务器可使用该命令。当前低内存 ECS 不应运行完整 `--build`；Web 和 Server 按下面的独立流程发布。

## 7. Web 发布：开发机构建，ECS 只接收静态文件

### 7.1 构建

在 Git Bash 中执行：

```bash
cd /d/Codex_Workspaces/software-development/projects/SyncBox-AI
bash deploy/scripts/build-web-local.sh https://app.example.com
```

脚本会：

1. 检查 Node 与 pnpm；
2. 执行 `pnpm install --frozen-lockfile`；
3. 通过 Turbo 强制重建 Web 及其 workspace 依赖，避免环境变量变化后命中旧 dist 缓存；
4. 验证 `apps/web/dist/index.html` 和 `assets`；
5. 输出文件数量和产物大小。

### 7.2 部署

```bash
bash deploy/scripts/deploy-web.sh \
  root@your-ecs \
  /c/Users/you/Desktop/server.pem \
  https://app.example.com
```

也可通过环境变量覆盖参数：

```bash
SSH_PORT=22 \
WEB_REMOTE_ROOT=/opt/inkweaver/web \
WEB_HEALTH_URL=https://app.example.com \
bash deploy/scripts/deploy-web.sh root@your-ecs /path/to/server.pem
```

部署脚本不依赖 `rsync`，其完整流程为：

1. 本地将 dist 打包为临时 tar.gz；
2. 计算 SHA-256；
3. 使用 scp 上传压缩包与受控远端辅助脚本；
4. 远端验证 SHA-256 和压缩包路径；
5. 解压到 `web.release.<release>`；
6. 验证 `index.html` 与 `assets`；
7. 继承现有目录所有者，并设置目录 `755`、文件 `644`；
8. 把旧目录暂存为 `web.previous.<release>`，再切换新目录；
9. 从开发机访问首页及页面引用的真实 JS/CSS；
10. 验收失败则恢复旧目录；验收成功则清除全部 `web.previous.*`、`web.backup.*`、`web.release.*` 和 `web.failed.*`。

成功后不保留 Web 历史发布备份。需要恢复旧代码时从 Git 重新构建并发布。

### 7.3 Web 验收

```bash
curl -fsSL https://app.example.com/ -o /tmp/inkweaver-index.html
grep -oE '/assets/[^" ]+\.(js|css)' /tmp/inkweaver-index.html | head
curl -I https://app.example.com/assets/<actual-file>.js
```

JS 应返回 JavaScript Content-Type，而不是 `text/html`。若 `/assets/*.js` 返回 HTML，通常是静态文件未上传、Nginx 无权读取，或 `/assets` 被错误回退到 SPA 的 `index.html`。

## 8. 低内存 ECS 的 Nest 发布

### 8.1 禁止的常规做法

当前 ECS 不要执行：

```bash
docker compose -p repo -f docker-compose.prod.yml --env-file .env.prod build --no-cache server
```

一次历史发布在依赖安装和 `nest build` 阶段造成 SSH、HTTPS 和 Shadowsocks 同时失去响应。旧启动周期没有保留下可核实的 OOM 日志，因此不能断言一定是 OOM；但可确定构建与整机资源耗尽同时发生。

### 8.2 推荐方式

长期方案是在开发机或 CI 构建 `linux/amd64` Server 镜像，推送到受控镜像仓库，ECS 只拉取并重新创建 Server。

当前紧急热修复方式只适用于依赖、Dockerfile 和运行时文件未变化：

1. 本机执行 `pnpm install --frozen-lockfile` 和 `pnpm build:server`；
2. 将完整 `apps/server/dist` 打包并计算 SHA-256；
3. 上传 ECS 并再次校验；
4. 以当前运行镜像为只读基线，仅覆盖 `/app/dist` 生成候选镜像；
5. 检查候选镜像中的关键文件和 Git 版本；
6. 临时标记当前镜像用于本次回滚；
7. 把候选镜像切换为 `repo-server:latest`；
8. 仅执行：

   ```bash
   docker compose -p repo -f docker-compose.prod.yml --env-file .env.prod \
     up -d --no-build --force-recreate server
   ```

9. 验证完成后删除本次临时回滚标签和旧的历史回滚标签。

该热修复不能用于 `package.json`、`pnpm-lock.yaml`、原生依赖、Dockerfile 或 entrypoint 变化。此时必须在开发机/CI 构建完整 `linux/amd64` 镜像。

### 8.3 迁移注意

Server entrypoint 默认先运行编译后的 TypeORM migration，再启动 Nest。除非已经证明数据库结构兼容，否则不要设置 `SKIP_MIGRATIONS=true`。

发布前检查迁移文件，先备份数据库，并在隔离的 PostgreSQL + pgvector 环境演练正向和回滚。`synchronize` 固定为 `false`，不能替代 migration。

### 8.4 防止旧 dist 再次上线

`docker compose up -d --build` 的成功退出不证明镜像包含最新源码。发布后至少验证：

```bash
docker inspect inkweaver-server --format '{{.Image}} {{.Config.Image}}'
docker run --rm --entrypoint sh repo-server:latest -c \
  "test -f /app/dist/main.js && find /app/dist -type f | head"
```

针对修复点再检查关键构建文件，例如 `grep` 对应符号或脚本。源码修改时间、镜像创建时间和镜像内 dist 内容三者必须一致。

## 9. 发布后统一验收

```bash
cd /opt/inkweaver/repo

docker compose -p repo -f docker-compose.prod.yml --env-file .env.prod ps
docker logs inkweaver-server --since 10m
curl -fsS http://127.0.0.1:3000/healthz
curl -fsS http://127.0.0.1:3000/readyz
curl -fsS https://app.example.com/
curl -fsS https://app.example.com/api/ai/ping
systemctl is-active nginx frps
docker ps --filter name=shadowsocks --format '{{.Names}} {{.Status}}'
```

验收至少覆盖：

- Server 没有重启循环、migration 异常或 Nest 依赖注入异常；
- PostgreSQL、Redis、MinIO 健康；
- 首页和静态资源 HTTP 200；
- `/readyz` HTTP 200；
- `/api/ai/ping` 中 Chat 和 embedding 状态符合当前环境；
- 带登录 Token 的 `/api/search/hybrid` 和 AI 问答返回真实结果；
- Shadowsocks 与 FRPS 未被发布操作影响。

匿名访问 `/api/search/hybrid` 返回 401 是 AuthGuard 的预期行为，不表示接口不通。

## 10. 首次启用或修复 AI 索引

```bash
docker exec inkweaver-server node dist/scripts/backfill-document-index.js
```

随后同时检查：

- 有效文档是否在 `document_chunks` 中有分块；
- BullMQ `ai-document-index` 是否存在 failed 任务；
- smart 搜索是否命中 fuzzy/semantic 通道；
- RAG 是否只展示模型实际使用的引用，而不是全部 Top-K 候选。

embedding `/embed` 返回 200 只能证明某次向量化成功，不能证明索引任务已入队或向量已写入数据库。

## 11. 典型问题速查

| 现象 | 根因或检查方向 | 正确处理 |
|------|----------------|----------|
| `pnpm: command not found` | 在 ECS 直接构建 Web | 回到开发机 Git Bash 运行 `build-web-local.sh` |
| `/bin/bash: No such file or directory` | 调用了 WSL bash，但本机未安装 WSL | 使用 Git Bash 的 `D:\Git\bin\bash.exe` |
| `rsync: command not found` | 旧脚本假定 Git Bash 带 rsync | 使用当前 scp/tar 部署脚本 |
| Web 构建显示 `cache hit` | Turbo 可能复用未反映构建环境变量的旧 dist | 发布脚本使用 `--force`，并检查新产物时间和内容 |
| `not a git repository` | 目录没有 `.git` | 保存 `.env.prod` 后重新 clone |
| `dubious ownership` | Git 用户与目录所有者不同 | 使用正确 Unix 用户或修正明确目录所有权 |
| 新 Nest 仍没有修复代码 | 镜像复用了旧 dist | 检查镜像内产物；低内存机使用外部构建方案 |
| Server migration 报 `efconstruction` | pgvector 参数名错误 | 使用 `ef_construction` |
| Nest 启动报 undefined module/provider | 循环依赖延迟注入不完整 | 检查完整 Provider 闭环和镜像内构建产物 |
| `/api/ai/ping` 路由 404 | 误判前端相对路径 | 前端 `/ai/ping` 会与 `/api` baseURL 合并为 `/api/ai/ping` |
| `embedHealthy=false` | 配置、FRP、UFW 或 stale frpc | 按内网穿透文档逐层验证 |
| AI 问答始终“找不到” | `document_chunks` 为空或任务失败 | 检查索引生命周期、队列和数据库，不只看 embedding 日志 |
| 引用显示 5 篇无关文档 | 把 Top-K 候选当实际引用 | 同时应用相关性阈值和回答引用过滤 |
| SSH/HTTPS/Shadowsocks 同时卡住 | 服务器资源耗尽 | 停止构建，通过云控制台恢复，先检查全部服务再继续 |

## 12. 回滚原则

- Web：脚本在验收前自动保留旧目录；验收失败自动恢复。成功后不保留历史目录。
- Nest：只在本次发布验收期间保留旧镜像标签；成功后清除。需要旧版本时按 Git commit 重新构建。
- 数据库：回滚应用前先判断 migration 是否向后兼容。不要只回滚镜像而忽略数据库结构。
- 业务数据：从已验证的 PostgreSQL/uploads 备份恢复；恢复属于高风险操作，必须单独确认目标和时间点。
